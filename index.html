Build & Compliance QA Checklist

Run this on every new site before it goes live. It covers California privacy (CCPA/CIPA), consent gating, and accessibility (WCAG 2.1 AA) — built into the WordPress / Elementor + WPConsent stack, not bolted on after.

P0

Foundation & Hosting

Get the environment and stack right before anything else.

  • Site on SiteGround (agency standard), HTTPS forced sitewideRedirect all HTTP→HTTPS, fix any mixed-content warnings.
  • Standard plugin stack installed — incl. WPConsent (consent), All in One SEO, Fluent Forms, Wordfence, caching/optimization
  • Confirm no leftover trackers from theme demos, migration, or a previous marketerOld SearchAtlas / GTM / pixel snippets love to hide in headers and footers.
P1

Tracking & Consent — the CIPA core

The whole game: nothing third-party fires before the visitor consents. A banner that shows but doesn't block is worse than none.

  • Inventory every third-party script the site loadsGA4, any ad pixels, chat widget, Google Maps, YouTube/Vimeo embeds, hosted fonts, heatmaps, booking/lead tools.
  • Configure WPConsent to BLOCK / script-gate all non-essential scripts until consent — not just display a notice
  • Banner has equal-prominence Accept & Decline (no buried reject), granular categories (necessary / analytics / marketing), and a withdraw-consent option
  • Banner links to Privacy Policy + Cookie Policy and is conspicuous (not footer-only)
  • GPC (Global Privacy Control) honored automatically — enable in WPConsent and test
  • Google Consent Mode v2 wired to the consent state; in GA4 turn off Google-signals / ad-data sharing and restrict IP handling
  • Chat widget: add a disclosure that a third-party vendor may access the conversation + consent before it opensApplies to Blazebo, HouseCall Pro lead capture, Jobber forms — anything where an outside party touches the message.
  • Embeds set to privacy mode: YouTube no-cookie, Maps consent-gated, fonts served locally where possibleEmbeds drop third-party cookies too — they count.
⚠ Drop the overlay shortcut. No AccessiBe / UserWay-style "accessibility widgets" and no auto-pixel plugins that fire on load. Overlays have been FTC-fined and don't hold up in court; real remediation is the only defensible path.
P2

Legal Pages

All present, accurate to what the site actually does, and linked in the footer.

  • Privacy Policy — matches real data collection & names every third-party vendor that receives data (Google, ad platforms, chat, etc.)
  • Cookie Policy — what cookies, their purpose, and duration
  • Terms of Service in place
  • Accessibility Statement with WCAG target level + a contact method for access issues
  • E-commerce only: clear purchase / pickup / refund terms; payments via a trusted processor (Square/Stripe) — never handle card data directly
⚠ Healthcare clients (clinics, chiro, dental): be far stricter. No marketing/analytics pixels on intake, booking, or condition pages — patient-page pixels are the most-litigated privacy fact pattern. Confirm HIPAA handling and whether the HHS §504 web-accessibility rule applies (Medicare/Medicaid funding).
P3

Accessibility — WCAG 2.1 AA, built in

Built into the markup, not added later. This is the Unruh-Act demand-letter shield.

  • Semantic structure: one H1 per page, logical heading order, proper landmarks
  • Alt text on all meaningful images; decorative images use empty alt=""
  • Color contrast meets AA — 4.5:1 body text, 3:1 large text & UI elements
  • Full keyboard operability + visible focus states on every interactive element
  • Form fields have visible labels (not placeholder-only), associated correctly, with clear error messages
  • Descriptive link text (no "click here"), info never conveyed by color alone, generous tap targets (mobile-first)
  • Skip-to-content link; captions/transcripts on any video or audio
Brand-color contrast catch: Neon Green #BFDF31 on white fails AA contrast (~1.6:1) — never use it for text or small UI on white. Use it as a background with dark ink text or as a decorative accent only. Royal Blue #004BFF on white passes for normal text.
P4

Pre-Launch Verification

Prove the behavior — don't assume the plugins did their job.

  • Run the 3-state network test (see box below) and confirm trackers are correctly gated
  • Banner matches behavior — if Decline is chosen, nothing fires (the "representational failure" trap)
  • Accessibility scan — Lighthouse / axe / WAVE clean, plus a manual keyboard-only pass and a screen-reader spot check (VoiceOver or NVDA)
  • GPC test — visit with a GPC-enabled browser/extension and confirm opt-out is auto-honored
  • All legal pages present & linked; HTTPS forced; no mixed content; mobile responsive with good tap targets
The 3-state network test (do this on every site)
Open the site, launch Chrome DevTools → Network tab, filter for third-party calls (e.g. google-analytics, googletagmanager, facebook, doubleclick), and check three states:
  1. No action (just landed, banner showing) → NO third-party tracking calls should fire.
  2. Decline / reject → trackers stay blocked.
  3. Accept → trackers now fire.
If anything calls out in state 1 or 2, the gating is broken — fix before launch.
P5

Document & Maintain

Documented good-faith effort is the legal defense. A fix today can be undone by an update tomorrow.

  • Save the record: tracker inventory, consent config, scan results, test screenshots, and dates — keep on file for the client
  • Re-run this checklist after major updates — new theme, plugin, page builder change, or any added tracker can break gating or accessibility
  • Periodic accessibility re-scan on maintained sites (content uploads reintroduce most issues)

Why this matters in one line: CIPA tracking suits ($5,000/violation) and Unruh accessibility demand letters have no business-size threshold — every client site needs this, and the consent gating + documented accessibility is what makes a site defensible.
